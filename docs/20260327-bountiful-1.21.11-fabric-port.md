## Building a Working Jar

Bountiful depends on **Kambrik**, which depends on **Percale**. All three must be built from source in order. The forked versions of these repos contain all required fixes for 1.21.11 and dedicated server compatibility.

### Prerequisites

- Java 21
- Git

### Step 1 — Clone the repos

```bash
mkdir BountifulDev && cd BountifulDev

git clone -b master git@github.com:kylerm42/Percale.git
git clone -b 1.21    git@github.com:kylerm42/Kambrik.git
git clone -b 1.21.11 git@github.com:kylerm42/Bountiful.git
```

### Step 2 — Build and publish Percale to mavenLocal

```bash
cd Percale
./gradlew :fabric:publishToMavenLocal -x test
cd ..
```

### Step 3 — Build and publish Kambrik to mavenLocal

```bash
cd Kambrik
./gradlew :fabric:publishToMavenLocal -x test
cd ..
```

> **Note:** You may need to also publish the common artifact if the Bountiful build fails to resolve it:
> ```bash
> ./gradlew :common:publishToMavenLocal -x test
> ```

### Step 4 — Build Bountiful

```bash
cd Bountiful
./gradlew :fabric:build -x test
```

The output jar will be at:

```
fabric/build/libs/bountiful-fabric-8.0.0-dev.2.jar
```

### Step 5 — Deploy

Copy to your instance's `mods/` folder alongside:

| Mod | Source |
|-----|--------|
| `bountiful-fabric-8.0.0-dev.2.jar` | Built above |
| `kambrik-fabric-8.0.0-dev.27.jar` | `~/.m2/repository/io/ejekta/kambrik/kambrik-fabric/8.0.0-dev.27/` |
| Fabric Loader 0.18.4+ | [fabricmc.net](https://fabricmc.net) |
| Fabric API 0.141.3+1.21.11 | [Modrinth](https://modrinth.com/mod/fabric-api) |
| Fabric Language Kotlin 1.13.10+kotlin.2.3.20 | [Modrinth](https://modrinth.com/mod/fabric-language-kotlin) |

> **Kambrik** is bundled as a jar-in-jar inside Kambrik itself (which includes Percale), so only the Kambrik jar needs to be in `mods/` — not Percale separately.

## Village Mod Compatibility (2026-03-28)

Investigated and resolved compatibility with Trek and CTOV village overhaul mods.

**CTOV** — Already compatible. CTOV ships its own `lithostitched/worldgen_modifier/bountiful/` files (one per village variant) that inject `bountiful:village/common/bounty_gazebo` into CTOV template pools, load-conditioned on `bountiful` being present. Requires Lithostitched to be installed for these modifiers to fire; no Bountiful code changes needed.

**Trek** — Not compatible out of the box. Trek overrides `minecraft:worldgen/structure_set/villages.json` to add `trek:village/*` structures (mod ID: `mr_trek`). These use `trek:village/<type>/houses` template pools — entirely separate from `minecraft:village/*/houses`. Bountiful's `registerJigsawPieces()` only injects into the vanilla pools, so Trek villages would never contain a bounty board.

**Fix:** Added 8 Lithostitched worldgen modifier files to Bountiful's own data:

```
common/src/main/resources/data/bountiful/lithostitched/worldgen_modifier/trek/
  plains.json       — uses bountiful:plains processor
  desert.json       — uses bountiful:desert processor
  savanna.json      — uses bountiful:savanna processor
  snowy.json        — uses bountiful:snowy processor
  taiga.json        — uses bountiful:taiga processor
  cherry.json       — uses minecraft:empty processor
  mushroom.json     — uses minecraft:empty processor
  swamp_vanilla.json — uses minecraft:empty processor
```

All files are gated with `fabric:load_conditions` on `mr_trek`. If Trek is absent, the modifiers are skipped silently. If Lithostitched is absent, the files are never processed. Lithostitched is **not** a required dependency of Bountiful — it is an optional dependency of the Trek integration only. No changes to `fabric.mod.json` are needed.

This pattern (data-driven Lithostitched modifiers, mod-ID-conditioned) is the canonical approach for adding bounty board support to any future village overhaul mod without touching Bountiful's code.

## DepthSolver Recipe Solver Fix (2026-04-07)

Fixed a logic bug in `DepthSolver.solveFor()` where craftable items with partially or fully unresolvable ingredient chains were incorrectly entering the Chaos Mode pool with a cost of `0.0`.

**Root cause:** `numUnsolvedIngredients` was initialized to `0` and only ever *decremented* (by `1`) when an ingredient slot was successfully resolved. The guard `if (numUnsolvedIngredients > 0)` — intended to discard recipes where some ingredients could not be costed — could therefore never fire. Unresolvable ingredient slots contributed `0.0` to `ingredientRunningCost` silently, and the recipe was always considered fully solved.

**Fix:** One line in `DepthSolver.kt` (~line 128):

```kotlin
// Before
var numUnsolvedIngredients = 0

// After
var numUnsolvedIngredients = inputSets.size
```

`numUnsolvedIngredients` now starts equal to the number of ingredient slots and counts down as each slot is resolved. If any slots remain unresolved, the recipe is correctly discarded and the item is excluded from the chaos pool (or resolved via another recipe if one exists).

**Impact:** Items with ingredient chains that trace back to unconfigured sources (modded items, tag ingredients with no known base cost) will no longer appear in the chaos pool priced at effectively free. Pool pricing accuracy for craftable items is improved.
